# 自动宿主激活、发现与原 Harness 上下文恢复

日期：2026-11-06；已登录桌面 WorkBuddy 5.6.2。操作者要求已写入 spec.md：Courier 独占实际用户 Harness 会话，桌面仅负责启动后端；FR-003/FR-009 逐字保留。

## 生产实现

普通连接配置在 ownership.mode=courier-exclusive 时，可省略 endpoint 和 bootstrapSessionRef 来选择自动模式，仍须正常提供 desktopDebugUrl、cwd、声明 CLI 版本及其他字段。手动固定端点模式保留；自动模式与固定 endpoint 互斥。

factory.ts 已接入 composeReal，负责解析实际运行目标、构造生产 WorkBuddyAdapter 和正常连接。平台准入检查先于宿主激活；全部 Harness 门槛仍先于 Stream 注册。

- 正常账户 API 确认登录后，调用一次 session:create 创建空白 H，不提交 Agent 任务。创建意图和结果写入私有适配映射；unknown/dispatching 阻止对象重建后的再次创建。
- runtime-discovery.ts 只识别同用户进程、已知厂商脚本和准确的启动宿主标识，再按进程持有的 socket inode 识别回环监听。只进行自有 ACP GET/DELETE 握手，不 initialize/load 用户上下文；多个匹配进程、未知服务或非回环目标不提供端点。
- 已知 H 保留并复用，启动时重新核对就绪及发现端点；H 忙碌、缺失或发现不确定时停止，不创建替代宿主。
- 实际用户 A/B 的所有权映射仍由生产适配器维护，H 不能承接用户输入。输出与恢复证据绑定实际目标和固定实现摘要；未知 CLI 版本的独立观察由工厂明确保留全部必需能力 unverified，不能用于正常服务准入。

## 镜像历史造成的实际重连缺陷

初始真实样本自动创建/发现 H，完成 A 首轮后，SQLite 重开时被宿主校验拒绝。后续只读诊断确认：H 标识、cwd、空闲和三类待处理均正确，但 57 帧历史中有 50 帧任务活动，全部关联 Courier 原 Run。桌面 SDK 会镜像 Courier 任务，并不代表桌面用户在 H 执行了独立任务；这些帧不是历史回放标记。

修复后，适配器在输入派发前持久化原 Run/输入关联，并只登记已证明的 steer owner；所有 start 模式统一携带原请求跟踪字段。宿主校验逐帧要求恰好一个已知 Run 证明组，所有提供的 owner/origin 字段均匹配，缺字段的工具结果还须对应已关联的原工具；外来、冲突或未绑定帧均拒绝。证明记录有界，损坏或超限不丢弃后放行。空闲与人工待处理检查保持。
