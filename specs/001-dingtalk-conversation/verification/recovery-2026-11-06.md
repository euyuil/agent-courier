# 核实结果与实际 Courier 子进程恢复

日期：2026-11-06。使用 Node.js 24.22.0、生产 Courier/SQLite/实例锁代码与进程外的测试 Harness、平台；无真实 WorkBuddy 或钉钉调用。

## 已复现和修复的生产缺陷

四项新增集成回归先失败，再修复：

- create/load 查询直接采用返回的 Harness 会话标识，遇到已归属其他 Courier 会话或不匹配原绑定的结果时依赖 SQLite 唯一性/不可变触发器阻止写入，并抛出 SQL 异常。已有数据库约束保护了原绑定；应用层现在先校验回执及已知归属，以 unknown/protocol_conflict 返回，不改变原标识、不发起新操作。
- start/steer/answer 查询即使回执被判为关联冲突，仍可能应用附带的 Run 状态。现在先检查原 Harness 会话、已知 Run、原人工请求和回执结构；缺失/外来运行标识、空依据及无明确未接收证明的拒绝均不能把 Run 改成完成。
- 查询等待期间已出现新的操作事实时，旧查询可能继续修改 Run。现在在短事务内重读事实；矛盾的接收/拒绝只记录协议冲突，保留新事实，不应用旧查询的状态。
- 正常查询确认 Run completed/failed 时，原有效人工请求没有同步关闭，失败或缺最终内容也未走原提示投影。现在同步关闭原 Run 的有效请求、保留原映射与答案事实，并生成一次对应限制提示。查询本身不发送消息。

统一 normalizeReceipt 另拒绝非字符串的 Harness 会话、运行任务、原请求标识或接收依据，既有契约回归同步扩展。查询返回明确 sessionAvailable=false 时保留绑定但标为 unavailable。

## 进程恢复边界

tests/fixtures/courier-process.ts 仅为离线驱动：子进程构造生产 Courier、打开仓库外临时 SQLite 并获取正常实例锁；Harness 和平台替身保留在父进程，通过本地 IPC 实现既有端口。它不启动真实适配器、不改准入，不提供生产网络入口。

tests/integration/process-recovery.test.ts 验证：

1. 首个 Courier 进程执行并投递两条同文 progress 与一条 final 后正常退出；第二个不同进程打开原库。原 Courier/Harness 绑定保留，旧入站重投与相同事件键重放均不重发，下一轮只 load 原 Harness 会话，进程外测试 Harness 保留两轮历史。
2. create、start、steer、answer、send 分别在 before_call、after_remote、after_commit 使用 SIGKILL，覆盖 15 个窗口；随后新进程重新取得实例锁并打开原库。
3. 未提交确认的操作/发送保持 unknown；已落盘的 accepted/delivered 保留。原消息重投、原答案再次提交及 flush 不重复原副作用；原人工请求编号、厂商标识和适配映射保留。
4. 发送尝试数不重置。首条发送未知时暂停后续；首条明确成功时可继续其余条目，但不再次发送首条。

这次确实终止并重建了 Courier 进程；外部 Harness 和平台仍是替身。它不证明桌面 WorkBuddy 写入权、真实 Agent 上下文恢复、钉钉投递，或运行中真实输出/人工请求的无损恢复。
